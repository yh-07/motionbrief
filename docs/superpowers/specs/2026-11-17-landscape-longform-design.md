# 横屏深度科普长视频（16:9，8–15 分钟）设计

- 日期：2026-11-17
- 状态：已批准（设计阶段），待用户审阅本文件后进入实施计划
- 目标平台：B 站、抖音横屏（共用一套 1080p 成片）

## 1. 目标与非目标

**目标**
- 在现有引擎上新增 16:9 长视频产线，输入为脚本（`inbox/`），输出为 `outbox/<id>/final.mp4`。
- 时长 8–15 分钟，面向工程师型科普受众。
- 视觉风格偏卡通，风格参考来自高赞 YouTube 科普视频的风格要素（不复制画面、素材或配乐）。
- 本会话的 token 消耗保持在低位：日常生产靠 `inbox` 流程，不需要 agent。

**非目标（本期不做）**
- 4K、60fps、封面图、直接上传 B 站或抖音。
- 把竖屏成片裁切成横屏，或反向派生。
- 改动竖屏已有的视觉风格和产出结果。

## 2. 画幅与共享分镜

- 脚本 front-matter 新增字段：
  - `aspect: 16:9 | 9:16`：主画幅，决定 `outbox/<id>/final.mp4` 的画幅，缺省为 `9:16`，旧脚本行为不变。
  - `also: [9:16]`（可选）：额外输出的画幅，产物为 `outbox/<id>/final_<aspect>.mp4`。
- **分镜只做一次**：shot plan 对两种画幅共用，同一份旁白、同一套镜头和同一个时间轴。分镜提示词只生成一次，不按画幅分叉。
- **shot plan 的坐标改为归一化**：位置用 0–1 的画布比例（如 `x: 0.5, y: 0.4`）或语义锚点（如 `top-third`、`center`），不写像素。渲染时按目标画布换算。
- 旧 plan（像素坐标，1080×1920）仍然有效，只允许用于 9:16，渲染时按原方式处理。新 plan 带 schema 版本号以区分。
- `motionbrief/ir/models.py` 中的画布模型由 `Literal["9:16"]` 改为由画幅推导宽高：
  - 16:9 → 1920×1080
  - 9:16 → 1080×1920
- `motionbrief/render/svg_canvas/scene.py` 中的 `W, H` 改为从 IR 画布读取，不再是常量。
- 组件按画幅使用各自的安全区和锚点映射。竖屏的映射保持现有输出不变，用现有 fixtures 做回归验证。横屏映射由组件逐个补充。
- 同一份 plan 在两种画幅下时长一致，因为时间轴由语音决定。

## 3. 时长与校验

- 16:9 脚本允许 480–900 秒（8–15 分钟）。
- 9:16 保持原有的 15–300 秒限制，Shorts 仍为 ≤180 秒。
- 校验按画幅分别判断，超出范围时 `motionbrief validate` 报错。

## 4. 章节卡

- 每个 `###` 章节开头插入一张标题卡，显示序号和标题，停留 2.5 秒，然后进入章节内容。
- 默认对 16:9 开启；9:16 默认关闭，可通过开关打开。

## 5. 分镜与质检

- 分镜提示词面向长视频科普：每章要有明确的机制讲解和视觉隐喻；章节仍按 `###` 切分，并行分镜。提示词要求输出归一化坐标，不再写 1080×1920 的像素。
- 确定性检查的语速阈值按画幅分开，横屏的每分钟信息密度可以低于竖屏。
- 多模态评审按画幅各跑一次，提示词分别为 16:9 和 9:16 版本。
- 事实核对：保留现有的事实核对表。16:9 脚本中每条事实性说法都必须有公开来源，缺来源则质检 gate 拒绝。

## 6. 卡通风格

- 基线为现有的 `Cartoon Tech v2` 风格。
- 横屏新增一套更偏卡通的风格包，挂在组件目录下，与竖屏风格互不影响。
- 风格要素的来源：通过代理检索 YouTube 高赞科普视频，人工归纳以下要素：配色、线条粗细、人物比例、镜头节奏、字幕样式、转场。
- 只学习风格，不抓取、复制对方的画面、素材、配乐或原片段。
- 风格规范整理成文档后再落到组件实现，不直接在组件代码中硬编码参考视频的参数。

## 7. 输出

- 横屏产物为 1920×1080，30fps，编码沿用现有 ffmpeg 链路。
- 主画幅产物为 `outbox/<id>/final.mp4`，额外画幅为 `outbox/<id>/final_<aspect>.mp4`。状态仍写入 `outbox/<id>/status.json`，记录每个画幅的渲染结果。
- 不写旋转元数据。横屏成片在抖音里的全屏效果由播放器决定，不在本项目实现。

## 8. 渲染与成本

- 默认在本机渲染（SVG 路径）。局域网渲染机（RTX 3060 Laptop）仅用于 Layer B（three.js toon）场景，当前空闲。
- 渲染机通过 SSH 访问，配置来自 `.env`，`MOTIONBRIEF_RENDER_HOST` 已设置。
- 分镜 LLM 的调用量比短视频多，由 qgenie 计费，不计入本会话。
- 渲染缓存：`ir/`、`render/svg_canvas`、`render/three`、`render/backend.py`、`render/ffmpeg.py` 的改动会使缓存全部失效。这类修改要合并成一批，渲染一次。
- 共享 plan 的收益：分镜和语音只做一次，两种画幅各自只需渲染。语音按"句子文本 + TTS 代码"缓存，两种画幅共用同一份音频。

## 9. 测试与验收

1. `motionbrief validate` 通过，覆盖 16:9 与 9:16 两种画幅的校验。
2. `pytest -q -m "not render"` 通过（约 10 秒）。
3. 竖屏回归：现有 fixtures 的产出不变。
4. 新增一个 16:9 的 fixture，并生成 animatic（约 1 分钟），人工审阅一次小尺寸预览图（宽 ≤800 px）。
5. 共享 plan 验证：同一份归一化 plan 分别渲染两种画幅，时长一致、时间轴一致；旧像素 plan 只允许用于 9:16。
6. 完整渲染前先与用户确认。
7. 发布前跑完整 `pytest`（约 2 分钟）。

## 10. 风险

- 8–15 分钟的渲染耗时和分镜成本明显高于短视频；第一次完整渲染前先估算。
- 现有组件有相当一部分是为竖屏设计的，横屏版面需要逐个组件检查。
- 风格研究依赖外部代理，检索结果受网络和平台策略影响。
- 组件的横屏适配工作量较大，按 CLAUDE.md 规则，批量组件改造交给 haiku 子代理，主会话只审阅小尺寸预览图。

## 11. 实施顺序（概要）

1. 归一化坐标 plan 的 schema 与旧像素 plan 的兼容，竖屏回归通过。
2. 画布参数化与 `aspect` / `also` 字段。
3. 时长校验与章节卡。
4. 分镜提示词（归一化坐标）与按画幅的质检阈值。
5. 风格研究（YouTube 与 B 站）→ 风格规范文档 → 横屏风格包。
6. 16:9 fixture 与 animatic 验证，两种画幅共享同一份 plan。
7. 用户确认后做完整渲染。
